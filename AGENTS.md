# SPEC76 Agent Operating Rules

## Назначение

Этот файл является единой точкой входа для управляемых ИИ-агентов, работающих с SPEC76. `CLAUDE.md` ссылается на этот документ и не дублирует правила.

## Язык и терминология

- Рабочий язык — русский.
- Каждый новый английский технический термин при первом употреблении пишется в формате: `English term (русский перевод)`, затем кратко объясняется смысл.
- Ответы должны разделять подтверждённые факты, предположения и рекомендации.

## Sources of Truth

- GitHub является Source of Truth (источником истины) для кода и инженерной документации.
- Supabase является Source of Truth (источником истины) для данных.
- Чат, память агента и локальные предположения не считаются источником истины.
- Нельзя утверждать существование файла, ветки, коммита, миграции, таблицы, политики RLS или завершённой проверки без фактического подтверждения.

## Обязательный контекст перед работой

Перед реализацией агент обязан проверить:

1. текущий Release (релиз);
2. связанную Capability (возможность платформы);
3. архитектурные зависимости и применимые ADR;
4. безопасность и политики RLS;
5. влияние на заказчика;
6. влияние на исполнителя;
7. простоту интерфейса;
8. миграции;
9. документацию и трассируемость;
10. Definition of Done (критерии завершения).

Обязательные нормативные документы:

- `engineering/constitution/PROJECT_CONSTITUTION.md`;
- `engineering/constitution/SPEC76_DIGITAL_CONSTITUTION.md`;
- `engineering/standards/SES-001_ENGINEERING_EXECUTION_STANDARD.md`;
- `engineering/standards/STD-001_DOCUMENTATION_STANDARD.md`;
- текущие документы Release, Capability, OP или EP.

## Режимы работы

- Architecture Mode (режим архитектуры) применяется при новом Release, изменении архитектуры, доменной модели, модели данных, существенном риске безопасности или необходимости решения Platform Owner.
- Execution Mode (режим исполнения) включается после сообщений «Утверждаю», «Приступаем», «Работаем» или иного однозначного подтверждения.
- В Execution Mode агент не повторяет утверждённый план, не просит подтверждение после каждого файла и ведёт пакет до проверяемого результата.
- Исполнение останавливается только при реальном блокере, противоречии фактов, архитектурном риске, юридическом риске, критическом дефекте или необходимости решения Platform Owner.

## Terminal и изменения файлов

- Для Terminal (терминала) предоставляются полные готовые команды с рабочей директорией и ожидаемым результатом.
- Частичные ручные правки файлов не предлагаются, когда безопаснее заменить файл целиком или применить проверенный скрипт.
- Сложность реализации не должна перекладываться на обычного пользователя.

## Инженерный цикл

Каждое изменение проходит применимые этапы:

1. Architecture Readiness Check (проверка архитектурной готовности);
2. Implementation (реализация);
3. Lint (статический анализ);
4. Type Check (проверка типов);
5. Tests (тесты);
6. Production Build (производственная сборка);
7. Diff Check (проверка различий);
8. Security Check (проверка безопасности);
9. Migration Check (проверка миграций);
10. Documentation Update (обновление документации);
11. Traceability Update (обновление трассируемости);
12. Git Commit (фиксация изменений);
13. Git Push (отправка в GitHub);
14. Working Tree Clean (чистое рабочее дерево).

Неприменимые этапы отмечаются явно.

## Quality Review Loop

Перед выдачей существенного решения агент обязан:

1. определить признаки сильного результата;
2. проверить соответствие архитектуре, Release, Capability, безопасности, UX, миграциям, документации и критериям завершения;
3. честно оценить решение;
4. найти и исправить слабые места;
5. повторить проверку до момента, когда дальнейшие изменения не дают существенного улучшения;
6. представить Platform Owner итоговые критерии, риски и итоговую оценку без публикации внутреннего чернового рассуждения.

## Human Approval Boundary

ИИ-агенты могут анализировать, рекомендовать и исполнять утверждённый инженерный пакет. Архитектурные, юридические, финансовые, репутационные и безопасностно значимые решения окончательно утверждает Platform Owner.

## Conversation to Repository

Переписка является рабочим материалом, но не нормативным источником. Подтверждённые решения и знания преобразуются по правилам `SES-001` и `STD-001` и фиксируются в существующих разделах SPEC76 OS без создания параллельной системы.

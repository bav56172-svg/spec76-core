Регламент описывает безопасную проверку и последующее применение Upgrade migration (миграции обновления — изменения существующей базы без пересоздания рабочих таблиц).

## 5. Репетиция

Предпочтительный вариант — отдельный временный Supabase-проект, восстановленный из подтверждённого PROD backup.

Минимальные условия репетиции:

1. Схема и данные `public` эквивалентны PROD.
2. Нужные пользователи присутствуют в `auth.users`.
3. До миграции сохранены количества строк и контрольные выборки.
4. Миграция выполняется целиком одной операцией.
5. Verification SQL выполняется целиком.
6. `overall_pass` равен `true`.
7. Количества `companies` и `projects` не изменились.
8. Связи `request_id` и `accepted_offer_id` не повреждены.
9. Выполнены положительные и отрицательные тесты RLS.

## 6. Стратегия истории миграций PROD

После успешной репетиции и отдельного решения Platform Owner:

1. Подтвердить PROD link.
2. Создать новый backup.
3. Зафиксировать checksum.
4. Пометить только старые Greenfield migration versions как applied в истории PROD без выполнения их SQL:
   - `20260724000100`;
   - `20260724000200`;
   - `20260728000100`.
5. Проверить `supabase migration list --linked`.
6. Dry run должен показывать только `20260801000100`.
7. Применить Upgrade migration.
8. Выполнить Verification SQL.
9. Создать post-upgrade schema dump и checksum.

Пункты 4–9 требуют отдельного утверждения Platform Owner непосредственно перед PROD execution (выполнением в PROD).

## 9. Условия остановки

Немедленно остановиться при:

- ошибке SQL;
- изменении количества компаний или проектов;
- `overall_pass = false`;
- появлении битых внешних связей;
- расширении доступа `anon`;
- потере законного доступа заказчика или исполнителя;
- несоответствии migration history;
- несовпадении checksum.

## 10. Rollback (откат)

Автоматический destructive rollback (разрушительный откат) не предоставляется.

Причины:

- миграция создаёт корректные записи членства;
- автоматическое удаление членства может уничтожить новую рабочую информацию;
- изменение RLS требует контролируемого решения.

При неуспешной репетиции временная среда удаляется и создаётся заново из backup.

При проблеме после PROD execution:

1. остановить пользовательские изменения;
2. сохранить post-failure dump;
3. зафиксировать incident;
4. Platform Owner выбирает:
   - исправляющую forward migration (миграцию вперёд);
   - восстановление базы из подтверждённого backup.

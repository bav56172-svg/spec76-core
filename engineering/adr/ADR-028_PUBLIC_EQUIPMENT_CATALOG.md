## Контекст

Оригинальное ТЗ описывает «Каталог услуг спецтехники» как отдельный от биржи заявок публичный модуль: витрина объявлений с поиском/фильтрами, доступная без входа в систему. Сейчас этого не существует: гость на главной странице видит только маркетинговый текст с CTA на `/auth`, никакой публичной страницы с данными нет.

Ближайшая существующая сущность — `public.company_equipment` (OP-023, `supabase/migrations/20260729000300_create_contractor_matching.sql`): `{ id, company_id, equipment_name, created_at }`. Используется только внутренним алгоритмом подбора (`services/contractorMatching.ts`), читать её могут только авторизованные пользователи. Ни категории, ни цены, ни фото, ни статуса публикации нет.

Supabase Storage в проекте не используется вообще (`grep "storage\."` по всем сервисам и миграциям — 0 совпадений). Таксономия категорий техники (15 пунктов из ТЗ: экскаваторы, автокраны, автовышки и т.д.) не существует ни в схеме, ни в типах.

`public.companies` уже имеет `city`, `description`, `phone`, `email`, `status` (добавлены в той же миграции, что и `company_equipment`).

## Решение

1. **Расширить `company_equipment`, а не создавать отдельную таблицу `Ads`** (как в оригинальном PRD). Это один и тот же реальный объект — единица техники компании. Добавляются колонки: `category` (16 значений: 15 из ТЗ + `other`), `price_hour`, `price_shift`, `description`, `cover_photo_path`, `status` (`draft`/`published`/`archived`, по умолчанию `draft`).
2. **Город объявления не дублируется на уровне записи** — берётся из `companies.city`. Явное упрощение MVP: у компании предполагается один город базирования техники. Если понадобится несколько точек — отдельное решение позже, не угадывается сейчас.
3. **Фото — одно (`cover_photo_path`), не галерея.** В ТЗ описана галерея фотографий; для MVP достаточно одного фото на объявление, чтобы проверить ценность модуля до вложений в полноценную медиа-галерею (в духе `PROJECT_CRITICAL_ASSESSMENT_AND_PLAN.md`: не строить весь продукт сразу).
4. **Новая RLS-политика на `company_equipment`**: публично (роль `anon`, не только `authenticated`) видны только записи со `status = 'published'` у компаний со `status = 'active'`. Существующие политики владельца компании не меняются.
5. **Новый Supabase Storage bucket `equipment-photos`**: публичное чтение, запись — только владелец компании по префиксу пути `{company_id}/...`.
6. **Публичные страницы (`app/catalog/*`) не защищены middleware** — он и так не перехватывает обычные страницы (matcher — только `/api/:path*` и `/admin/:path*`), RLS делает всю работу по ограничению видимости данных.

## Альтернативы

- **Отдельная таблица `Ads`, как в оригинальном PRD** — отклонено: дублирует понятие «единица техники компании», которое уже есть в `company_equipment`; расхождение данных между двумя таблицами про одно и то же было бы неизбежно.
- **Галерея из нескольких фото в этой же версии** — отклонено: больше инфраструктуры (упорядочивание, лимиты, отдельная таблица `equipment_photos`) без проверенной необходимости на этом этапе.
- **Город на уровне объявления отдельным полем** — отклонено для MVP: добавляет поле, для которого сейчас нет ни одного сценария с несколькими городами у одной компании.

## Последствия

- `company_equipment` обслуживает теперь две задачи: внутренний подбор исполнителей (OP-023) и публичную витрину (OP-034). Записи, которые не предназначены для публикации, остаются `status = 'draft'` — не видны публично, но всё ещё участвуют в подборе (RLS для `contractorMatching.ts` не меняется, доступ для авторизованных пользователей не сужается).
- Появление анонимного (`anon`) доступа к таблице, которая раньше была полностью закрыта авторизацией — требует аккуратной формулировки RLS (двойное условие: статус объявления И статус компании), проверяется на `apps-serve` до слияния.

## Риски

- Анонимный доступ к данным — любая ошибка в RLS-условии может случайно раскрыть неопубликованные объявления или объявления компаний в статусе `suspended`/`archived`. Проверяется явным тестом (опубликовать запись у `draft`-компании и у `active`-компании, убедиться в разной видимости) перед слиянием.
- Storage bucket с публичным чтением — путь файла не должен допускать перечисление (enumeration) чужих `company_id`; загрузка возможна только владельцем, но публичное чтение по прямой ссылке — ожидаемое поведение для фото объявлений (не секретные данные).

## 1. Контекст

Первоначальная версия EP-024 проектировалась для чистой TEST-среды, где была подтверждена только Billing-схема. Последующий аудит подтвердил, что Production уже содержит действующую доменную платформу: `companies`, `projects`, `requests`, `offers`, `tasks`, документы, обсуждения, уведомления, проектные события, этапы и календарные планы.

`companies` и `projects` являются центральными сущностями с внешними ключами, индексами, триггерами и действующими RLS-политиками. Поэтому миграция, безопасная для чистой установки, не является автоматически безопасной для обновления Production.

## 2. Решение

EP-024 развивает существующую платформу без потери данных и без удаления подтверждённых пользовательских связей.

Устанавливаются два независимых пути:

1. Greenfield migration (миграция чистой установки) — создание платформы в новой пустой среде.
2. Upgrade migration (миграция обновления) — совместимое преобразование существующей Production-схемы.

Production не изменяется до отдельного решения Platform Owner после успешной проверки Upgrade migration в безопасной среде, эквивалентной Production.

## 3. Архитектурные инварианты

### 3.1 Идентичность

- `auth.users` остаётся единственным источником Authentication (аутентификация — подтверждение личности пользователя).
- `profiles.id` связывается с `auth.users.id` отношением один к одному.
- `profiles` не хранит пароли, токены или замену Supabase Auth.

### 3.2 Компании

- `companies` остаётся существующей центральной доменной сущностью.
- Существующие идентификаторы и внешние связи сохраняются.
- `companies.owner_id` сохраняется как поле ответственного владельца, но не остаётся единственным механизмом Authorization (авторизация — проверка разрешённых действий).
- Вводится `company_members`.
- Для каждого существующего владельца создаётся активное членство с ролью `owner`.
- Поля `description`, `phone`, `email`, `city`, `status` не удаляются.
- `slug` может добавляться только после проверки данных, правил генерации, конфликтов и влияния на интерфейс.

### 3.3 Членство

- `company_members` расширяет существующую модель, а не заменяет пользовательские данные.
- Роли: `owner`, `admin`, `member`.
- Состояния: `active`, `suspended`, `removed`.
- Пара `(company_id, user_id)` уникальна.
- Клиент не может самостоятельно назначать себе `owner` или `admin`.

### 3.4 Проекты

- Существующие идентификаторы и ссылки на `projects.id` сохраняются.
- `company_id`, `owner_id`, `request_id`, `accepted_offer_id` сохраняются на первом этапе обновления.
- Уникальные ограничения и внешние ключи сохраняются, пока отдельный ADR не утвердит иную модель.
- Каноническое пользовательское поле проекта остаётся `title`.
- Переименование `title` в `name` не входит в первую Upgrade migration.

### 3.5 Зависимые модули

EP-024 не удаляет и не обнуляет связи `requests`, `offers`, `tasks`, `documents`, `conversations`, `notifications`, `project_activities`, `project_milestones`, `project_timelines`.

## 4. Целевая модель

### `profiles`

- `id uuid primary key references auth.users(id) on delete cascade`;
- `display_name text null`;
- `avatar_url text null`;
- `created_at timestamptz not null`;
- `updated_at timestamptz not null`.

### `companies`

Сохраняются минимум: `id`, `owner_id`, `name`, `description`, `phone`, `email`, `city`, `status`, `created_at`, `updated_at`.

### `company_members`

- `id uuid primary key`;
- `company_id uuid not null references companies(id) on delete cascade`;
- `user_id uuid not null references auth.users(id) on delete cascade`;
- `role company_member_role not null`;
- `status company_member_status not null default 'active'`;
- `created_at timestamptz not null`;
- `updated_at timestamptz not null`;
- `unique(company_id, user_id)`.

### `projects`

Сохраняются минимум: `id`, `company_id`, `owner_id`, `request_id`, `accepted_offer_id`, `title`, `description`, `status`, `created_at`, `updated_at`.

`created_by` может добавляться только совместимой миграцией с определённым источником данных для существующих строк.

## 5. RLS-стратегия

RLS (Row Level Security — безопасность на уровне строк) изменяется поэтапно:

1. Инвентаризация действующих политик, ролей, операций и серверных функций.
2. Создание `company_members` и заполнение владельцев без удаления действующих политик.
3. Введение функций доступа с фиксированным `search_path`, минимальными привилегиями, без динамического SQL и без рекурсии RLS.
4. Переключение политик только после положительных и отрицательных SQL-тестов.

Новая модель не должна открывать чужие данные, блокировать законный доступ или нарушать сценарии заказчика и исполнителя.

## 6. Greenfield migration

Greenfield migration создаёт целевую схему в пустой среде, включает безопасную RLS, транзакционное создание компании и владельца-члена и должна воспроизводиться после полного локального reset.

Greenfield migration не является доказательством безопасности Upgrade migration.

## 7. Upgrade migration

Upgrade migration использует преимущественно `ALTER TABLE`, создание новых объектов и безопасное заполнение данных.

Она не должна:

- пересоздавать `companies` или `projects`;
- изменять существующие UUID;
- удалять данные или подтверждённые связи;
- применять `NOT NULL` до проверки и заполнения данных;
- удалять RLS-политики до проверки замены.

Минимальная последовательность:

1. проверить качество существующих данных;
2. создать `profiles`;
3. создать `company_members`;
4. заполнить членство владельцев;
5. проверить полноту и уникальность;
6. добавить функции доступа;
7. выполнить SQL-тесты;
8. ввести совместимые политики;
9. сравнить доступ до и после;
10. только затем удалить заменяемые политики.

## 8. Влияние на заказчика и исполнителя

- Существующие компании, проекты и связи заявка → предложение → проект сохраняются.
- Внутренняя миграционная сложность не показывается пользователю.
- Членство создаёт основу для многокомандной работы.
- Ошибки доступа остаются понятными пользовательскими сообщениями.

## 9. Альтернативы

### Применить чистую миграцию непосредственно к Production

Отклонено из-за риска конфликтов, потери полей, связей и доступа.

### Пересоздать доменную модель

Отклонено из-за риска потери данных и нарушения непрерывности пользовательских процессов.

### Оставить только `owner_id`

Отклонено как целевая модель, но допускается временно для совместимого перехода.

### Удалить `request_id` и `accepted_offer_id`

Отклонено: поля подтверждены в Production и защищены внешними ключами и уникальными индексами.

### Переименовать `title` в `name`

Отклонено для первой Upgrade migration из-за риска несовместимости.

## 10. Последствия и риски

Положительные последствия: сохранение данных и процессов, контролируемое внедрение членства, независимая проверка чистой установки и обновления.

Отрицательные последствия: несколько миграций, переходный период с `owner_id`, дополнительные SQL-тесты и более сложная внутренняя реализация.

Основные риски: неполный backfill (заполнение существующих данных), рекурсия RLS, потеря законного доступа, расширение доступа, несовпадение Greenfield и Upgrade схем, несовместимость TypeScript-контрактов.

## 11. Architecture Readiness Check

Перед SQL Implementation (реализация SQL — создание или изменение объектов базы данных) необходимо подтвердить Release 0.4, C-002, фактическую Production-схему, качество данных, внешние ключи, индексы, триггеры, RLS, пользовательские сценарии, оба миграционных плана, rollback plan (план отката) и критерии завершения.

## 12. Критерии завершения EP-024

- ADR-024 зарегистрирован и принят.
- EP-024 соответствует ADR.
- Greenfield migration воспроизводится локально.
- Upgrade migration проверена на схеме, эквивалентной Production.
- Данные, идентификаторы и связи сохранены.
- Владельцы имеют активное членство `owner`.
- RLS проверена положительными и отрицательными тестами.
- Сервисы не используют `owner_id` как единственный механизм доступа.
- Lint, TypeScript, Production Build, Diff Check и Migration Check проходят.
- Документация обновлена.
- Production не изменён без отдельного решения Platform Owner.

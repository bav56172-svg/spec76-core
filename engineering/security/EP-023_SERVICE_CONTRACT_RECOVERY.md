# EP-023 — Service Contract Recovery

**Версия:** 0.1
**Статус:** In Progress (в работе)
**Владелец:** Platform Owner (владелец платформы)
**Release:** 0.4
**Ветка:** `engineering/ep-023-security-recovery`

## Architecture Readiness Check

Выбран первый вертикальный срез доменного потока:

`Request → RequestAnalysis → ContractorMatch → Offer`

Причина выбора: этот поток входит в Release 0.4, отражён в Traceability Matrix и используется пользовательским интерфейсом заявки.

## Реализованный фундамент

Добавлены:

- `ServiceResult<T>` — единый результат сервисной операции;
- `ServiceError` — единая безопасная ошибка сервисного слоя;
- стабильные коды ошибок;
- фабрики успешного и ошибочного результата;
- преобразование ошибок Supabase в доменный контракт.

## Мигрированный вертикальный срез

На единый контракт переведены:

- `services/requests.ts`;
- `services/requestAnalysis.ts`;
- `services/contractorMatching.ts`;
- `services/offers.ts`.

Публичная форма `{ data, error }` сохранена для совместимости текущего интерфейса.

## Security Boundary

- сервисный слой не возвращает необработанную структуру ответа Supabase;
- техническая причина может сохраняться в `cause`, но пользовательский интерфейс использует безопасное `message`;
- проверка прав остаётся обязанностью Supabase RLS и серверных границ;
- данный пакет не изменяет политики RLS и схему базы данных.

## Migration Check

Миграции Supabase не требуются: схема данных и политики RLS не изменяются.

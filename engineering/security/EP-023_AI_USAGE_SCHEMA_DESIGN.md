# Purpose (назначение)

Документ определяет архитектурную модель будущей сущности `ai_usage`.

Документ не создаёт Supabase migration (миграцию Supabase).

Цели:

- контроль использования AI Operations (ИИ-операций);
- аудит операций;
- подготовка безопасной модели лимитов;
- сохранение контроля человека.

---

# Confirmed Context (подтверждённый контекст)

Подтверждено:

- Release 0.4 активен;
- C-006 AI Request Foundation утверждена;
- ADR-025 утверждён;
- EP-023 AI API Data Security Foundation создан;
- AI API routes отсутствуют;
- AI provider не подключён;
- таблица `ai_usage` отсутствует.

EP-024 подтвердил существующую модель:

- `profiles`;
- `companies`;
- `company_members`;
- `projects`;
- существующий RLS.

---

# Data Model Decision (решение по модели данных)

Будущая сущность:

public.ai_usage

является журналом использования AI Operations (ИИ-операций).

Назначение:

- контроль лимитов;
- аудит;
- защита от неконтролируемых операций.

`ai_usage` не является источником бизнес-данных.

---

# Access Model (модель доступа)

AI Operations использует существующую модель:

User
 |
Company Membership
 |
Company
 |
Project
 |
AI Usage

Отдельная система прав для AI Usage не создаётся.

Доступ определяется:

- принадлежностью к компании;
- доступом к проекту;
- ролью пользователя.

---

# Proposed Fields (предлагаемые поля)

Будущая структура должна учитывать:

- идентификатор операции;
- пользователя;
- компанию;
- проект;
- тип операции;
- статус выполнения;
- технические метрики;
- временные отметки.

Идентификаторы пользователей должны поступать из серверного контекста.

Клиент не передаёт:

- user_id;
- права доступа;
- владельца операции.

---

# RLS Strategy (стратегия RLS)

Будущие политики должны использовать существующую модель доступа EP-024.

Доступ определяется:

- принадлежностью к компании;
- доступом к проекту;
- ролью пользователя.

Не использовать только:

user_id = auth.uid()

как единственный критерий доступа.

Пользователь не получает доступ к AI Usage только по факту создания записи.

---

# Reservation Lifecycle (жизненный цикл резервирования)

Операция проходит стадии:

request received

↓

reservation created

↓

AI execution

↓

completed / failed

Каждая стадия должна быть контролируемой и аудируемой.

---

# Atomic Function Requirement (требование атомарной функции)

Будущая серверная функция должна атомарно выполнять:

1. проверку лимита;
2. создание reservation;
3. фиксацию результата.

Запрещено использовать последовательность:

read limit

↓

write usage

без защиты от конкурентных запросов.

---

# Rollback Strategy (стратегия отката)

При невозможности безопасного завершения:

- новая схема не переводится в активное использование;
- выполняется обратимая миграция согласно проверенной процедуре;
- существующие данные не удаляются автоматически;
- результат отката фиксируется в инженерном журнале.

---

# Implementation Boundary (граница реализации)

До отдельного утверждения запрещено:

- создавать таблицу `ai_usage`;
- создавать Supabase migration;
- подключать AI provider;
- создавать API route;
- изменять RLS.

Следующий этап:

- проектирование Supabase migration;
- RLS test plan;
- atomic function design.

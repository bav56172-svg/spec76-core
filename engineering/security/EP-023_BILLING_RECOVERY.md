## Архитектурное решение

Billing Recovery разделяет данные на три области ответственности:

1. `billing_customers` — связь пользователя SPEC76 с Stripe Customer (клиентом Stripe).
2. `billing_subscriptions` — серверное состояние подписки.
3. `billing_webhook_events` — приватный журнал Idempotency (идемпотентности — защиты от повторной обработки одного события) и аудита.

Одна универсальная таблица `billing` не создаётся.

## Миграция

Подготовлен файл:

`supabase/migrations/202607190001_ep_023_billing_recovery.sql`

Миграция создаёт:

- первичные ключи UUID;
- внешние ключи на `auth.users`;
- уникальные ограничения Stripe Customer и Stripe Subscription;
- составной внешний ключ, исключающий связь подписки с чужим пользователем;
- проверку допустимых статусов подписки;
- проверку периода подписки;
- индексы для пользовательских, Stripe и операционных запросов;
- автоматическое обновление `updated_at`;
- RLS с принудительным применением;
- пользовательский доступ только на чтение собственных customer/subscription строк;
- полный запрет пользовательского доступа к журналу webhook;
- серверные права для `service_role`.

## RLS-модель

### `billing_customers`

Authenticated user (аутентифицированный пользователь) может выполнять только `SELECT` собственных строк по условию:

```sql
auth.uid() = user_id
```

Пользовательские `INSERT`, `UPDATE` и `DELETE` не разрешаются.

### `billing_subscriptions`

Authenticated user может выполнять только `SELECT` собственных строк по условию:

```sql
auth.uid() = user_id
```

Пользовательские `INSERT`, `UPDATE` и `DELETE` не разрешаются.

### `billing_webhook_events`

Пользовательские политики отсутствуют. Таблица доступна только доверенному серверному процессу.

## Security by Design

- Stripe identifiers (идентификаторы Stripe) записывает только сервер.
- Финансовое состояние не изменяется из браузера.
- Повторное событие блокируется уникальным `stripe_event_id`.
- Подписка связывается с конкретным пользователем через составной внешний ключ.
- Raw payload (необработанное содержимое события) не должен сохраняться целиком без необходимости; поле `event_payload` предназначено только для минимизированных данных аудита.
- Обычный пользователь не видит внутреннюю механику Stripe и webhook.

## Webhook Recovery

Новый webhook:

1. проверяет подпись Stripe по исходному телу запроса;
2. использует серверный `service_role` только внутри серверного модуля;
3. регистрирует уникальный `stripe_event_id` до изменения состояния подписки;
4. обрабатывает повторную доставку события без повторного финансового изменения;
5. ищет пользователя через `billing_customers`, а не доверяет внешним metadata;
6. обновляет подписку только по конкретному `stripe_subscription_id` и связанной записи пользователя;
7. проверяет количество изменённых строк;
8. сохраняет минимизированный журнал обработки;
9. не возвращает внутренние ошибки и секреты во внешний ответ.

## Влияние на пользователей

### Заказчик

Получает только понятный статус тарифа и подписки. Внутренние Stripe-идентификаторы и журнал событий в интерфейсе не показываются.

### Исполнитель

Billing не влияет на выполнение работ напрямую. Исполнитель не получает доступа к платёжным данным заказчика.

## Migration Check

До применения в production (продуктивной среде) необходимо выполнить:

1. применить миграцию в тестовом Supabase-проекте;
2. повторно получить структуру таблиц, индексов, ограничений и RLS;
3. проверить чтение собственной строки authenticated-пользователем;
4. проверить невозможность чтения чужой строки;
5. проверить невозможность пользовательских `INSERT`, `UPDATE` и `DELETE`;
6. проверить отсутствие доступа к `billing_webhook_events`;
7. проверить повторную вставку одинакового `stripe_event_id`;
8. проверить откат миграции на отдельной тестовой базе;
9. получить окончательное утверждение Platform Owner.

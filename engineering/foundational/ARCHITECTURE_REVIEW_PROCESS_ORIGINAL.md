Этот документ описывает **другой, гораздо более формальный инженерный процесс**, чем тот, что реально используется в проекте (`SES-001`, `OP-XXX`-нумерация, `ADR-0XX` в три цифры типа `ADR-024`). Конкретные несовпадения:

Фактическая реализация — монолит на Next.js + Supabase Auth напрямую, без выделенных микросервисов аутентификации/идентичности.
- **Описывает процесс (RTF — предположительно "Requirements To Fulfillment" или аналог), которого нет ни в `AGENTS.md`, ни в `SES-001`**: Draft Functional Requirement → Review → Approval → Architecture Review → ADR Development → ADR Approval → ADR Compliance Check → RTM Update → Implementation → Verification & Testing. - Структура требований `FR-1500` (Epic "Users & Identity") → `FR-1510` User Registration, `FR-1520` Authentication, `FR-1530` Authorization & Roles и т.д. — такой нумерации требований (`FR-XXXX`) больше нигде в репозитории не встречается.

### Часть 1 — Architecture Review ST76-AR-001 для FR-1520 "Аутентификация"

**Вывод**: аутентификация выходит за рамки ответственности `Identity Service` (`ADR-0033`, который отвечает за регистрацию/создание учётной записи/подтверждение контактов/управление состоянием записи). Требуется новый самостоятельный домен и сервис — **`ADR-0034` — Authentication Service**.

**Решение `ADR-0034`**: создать самостоятельный доменный сервис Authentication Service, отвечающий исключительно за процессы аутентификации пользователей. Взаимодействует с Identity Service через внутренние контракты, не управляя жизненным циклом учётных записей.

Входит в ответственность: выполнение процесса аутентификации; проверка допустимости входа; применение политик безопасности входа; обработка успешных/неуспешных попыток; управление жизненным циклом процесса аутентификации; публикация событий аутентификации; аудит входа.

Не входит в ответственность: регистрация пользователей; создание/изменение учётных записей; подтверждение контактных данных; управление профилем; авторизация и управление ролями; управление организациями; долгосрочное хранение идентификационных данных.

Интеграции: входящие — Public Authentication API, внутренние вызовы доверенных сервисов; исходящие — Identity Service (состояние учётной записи), Audit Trail (события входа/выхода/отказов), Event Bus (доменные события), Notification Domain, Analytics Service.

Статус по итогу: `ADR-0034` утверждён (Approved), ADR Compliance Check — Passed. RTM обновлена, полная трассируемость: `FR-1520 → Architecture Review → ADR-0034 → ADR Compliance Check → RTM`.

### Часть 2 — Draft и Review FR-1530 "Авторизация и управление ролями"

FR-1530 определяет функциональные требования к подсистеме авторизации: какие действия может выполнять уже аутентифицированный пользователь, в соответствии с ролями, разрешениями и политиками доступа. Явно не определяет архитектурную реализацию.

Область применения: физические лица; индивидуальные предприниматели; представители организаций; сотрудники платформы; системные/сервисные учётные записи.

Функциональные требования (сжато): проверка полномочий перед доступом; единообразное решение об авторизации независимо от вызывающего сервиса; учёт ролей/разрешений/политик; учёт изменений полномочий при последующих проверках; однозначный результат ("доступ разрешён"/"доступ запрещён"); доступность решений для аудита; расширяемость новыми ролями и политиками без изменения базовой модели.

Business Rules: авторизация выполняется только после успешной аутентификации; отсутствие разрешения → отказ в доступе; роли/разрешения логически независимы от механизма аутентификации; все решения подлежат аудиту; политики доступа централизованы и единообразны по всей платформе.

Явно НЕ определяет (отложено до Architecture Review): архитектуру сервиса авторизации; внутренние API; модель хранения ролей; механизм вычисления политик доступа; формат токенов/claims; модель контроля доступа (RBAC/ABAC/ReBAC или комбинация).

**Рекомендации по итогам Review** (не требуют изменения FR-1530 сейчас, к рассмотрению позже):
- в `FR-1550` определить модель наследования полномочий для организаций и их представителей;
- в `FR-1560` описать влияние изменения ролей на уже существующие пользовательские сессии;
- во время Architecture Review отдельно оценить необходимость выделения самостоятельного **Authorization Service** — проверка политик доступа может оказаться отдельной Domain Capability и потребовать своего ADR.

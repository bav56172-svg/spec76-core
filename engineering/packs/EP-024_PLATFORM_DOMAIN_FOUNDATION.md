## Цель

Развить доменную основу SPEC76 для профилей, компаний, членства и проектов без потери Production-данных и без нарушения действующих пользовательских процессов.

## Подтверждённый контекст

- Greenfield-схема EP-024 воспроизводится локально.
- Billing-таблицы совместимы между EP-024 и Production.
- Production содержит существующую доменную платформу.
- `companies` и `projects` имеют внешние ключи, индексы, триггеры и RLS.
- `projects` связан с `requests` и `offers`.
- Прямая миграция чистой схемы в Production небезопасна.
- Production не изменяется на текущем этапе.

## Scope (область работ)

- `profiles` и `company_members`;
- совместимое развитие `companies` и `projects`;
- backfill (заполнение существующих данных) владельцев компаний;
- функции доступа и поэтапное обновление RLS;
- Greenfield migration и Upgrade migration;
- SQL-тесты;
- обновление типов, сервисов, документации и трассируемости.

## Out of Scope (не входит в работу)

- удаление `requests`, `offers`, `tasks` или существующих проектных связей;
- немедленное удаление `projects.owner_id`;
- переименование `projects.title`;
- приглашения и `project_members`;
- юридическая верификация компаний;
- изменение Production без отдельного утверждения.

## Контуры реализации

### 1. Documentation Recovery

Принять и зарегистрировать ADR-024, обновить EP-024, ADR Index, ADR Registry, Release Backlog и Current Sprint, затем выполнить Diff Check.

### 2. Data Readiness

Проверить `companies`, `projects`, nullable-поля, владельцев, статусы, уникальность связей и допустимость новых ограничений без изменения Production.

### 3. Migration Design

Подготовить отдельно Greenfield migration, Upgrade migration, data backfill, rollback plan и SQL verification plan.

### 4. Security

Инвентаризировать RLS, создать безопасные функции членства, исключить рекурсию, проверить положительные и отрицательные сценарии и доказать отсутствие расширения доступа.

### 5. Application Contracts

Обновить типы и сервисы, сохранить `title`, связи заявок и предложений и прекратить использование `owner_id` как единственного механизма доступа.

### 6. Validation

Lint, TypeScript, Production Build, Diff Check, Migration Check, SQL access tests, документация и Git Commit.

## Security Requirements (требования безопасности)

- `auth.users` остаётся источником идентичности;
- анонимный доступ к закрытым данным запрещён;
- членство добавляется без преждевременного удаления политик;
- клиент не назначает себе административные роли;
- функции имеют фиксированный `search_path`;
- динамический SQL не используется;
- RLS-рекурсия исключается тестами;
- Production не изменяется.

## Влияние на заказчика и исполнителя

Компании, проекты и связи с заявками и предложениями сохраняются. Внутренняя миграционная сложность не показывается пользователю. Членство создаёт основу для многокомандной работы.

## Migration Plan (план миграции)

### Greenfield

1. Применить миграции к чистой локальной базе.
2. Проверить структуру и RLS.
3. Выполнить полный reset.
4. Проверить повторяемость.

### Upgrade

1. Воспроизвести Production-схему в безопасной среде.
2. Выполнить Data Readiness Audit.
3. Создать новые таблицы и функции.
4. Заполнить членство владельцев.
5. Проверить полноту данных.
6. Ввести совместимые RLS-политики.
7. Выполнить SQL-тесты.
8. Сравнить схему до и после.
9. Не применять к Production без отдельного утверждения.

## Definition of Done (критерии завершения)

- ADR-024 принят и зарегистрирован.
- Документация соответствует фактической Production-схеме.
- Greenfield и Upgrade migrations существуют и проверены.
- Идентификаторы, данные и связи сохранены.
- Владельцы имеют членство `owner`.
- RLS проверена положительными и отрицательными тестами.
- Сервисы используют членство.
- Lint, TypeScript, Production Build, Diff Check и Migration Check проходят.
- Production не изменён.

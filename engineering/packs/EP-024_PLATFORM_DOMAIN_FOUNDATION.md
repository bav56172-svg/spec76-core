# EP-024 — Platform Domain Foundation Engineering Package

**Версия:** 0.1
**Статус:** Architecture
**Владелец:** Platform Owner
**Release:** 0.4
**ADR:** `engineering/adrs/ADR-024_PLATFORM_DOMAIN_FOUNDATION.md`
**Базовый коммит EP-023:** `364ee1980a0a8fd4520e4dd44b52193ad3b260ea`

## Цель

Создать минимальное архитектурно завершённое доменное ядро SPEC76 для пользователей, компаний, членства и проектов до продолжения EP-023 и реализации AI Usage.

## Подтверждённый контекст

- TEST Supabase содержит только подтверждённую Billing-схему.
- История миграций GitHub и TEST синхронизирована на `202607190001_ep_023_billing_recovery.sql`.
- Приложение ожидает таблицы `companies`, `projects`, `tasks`, `requests`, `offers` и `ai_usage`.
- Подтверждённые доменные миграции для этих таблиц отсутствуют.
- `services/companies.ts` использует `owner_id` как текущую модель доступа.
- `services/projects.ts` зависит от ещё не восстановленных прикладных модулей.

## Scope (область работ)

В EP-024 входят:

- `profiles`;
- `companies`;
- `company_members`;
- `projects`;
- общие функции проверки доступа;
- RLS для всех таблиц ядра;

- обновление TypeScript-типов и сервисов компаний и проектов;

- документация.

## Out of Scope (не входит в работу)

- `ai_usage`;

## Security Requirements (требования безопасности)

- `auth.users` остаётся источником идентичности;
- анонимный доступ к ядру запрещён;
- доступ к компании определяется активным членством;
- доступ к проекту наследуется от активного членства компании;
- клиент не может назначить себе `owner` или `admin`;
- `created_by` и `owner_id` не принимаются как доверенные клиентские значения;
- физическое удаление компании обычным пользователем запрещено;
- функции доступа используют фиксированный `search_path`;
- Production не изменяется.

## Влияние на заказчика

- организация и проекты доступны только уполномоченным участникам;
- создание компании остаётся одной понятной операцией;
- техническая модель членства не показывается без необходимости;
- ошибки доступа формулируются как понятные пользовательские сообщения.

## Влияние на исполнителя

- один пользователь сможет состоять в нескольких компаниях;
- будущий доступ к отдельным проектам можно добавить без изменения ядра;
- роли не связываются с типом личности навсегда и могут назначаться в контексте компании.

## Migration Plan (план миграции)

1. Создать миграцию ядра после принятия ADR.
2. Проверить применение в чистой локальной или временной TEST-среде.
3. Проверить SQL-сценарии доступа.
4. Применить только к связанному TEST после успешных проверок.
5. Сравнить локальную и удалённую историю миграций.
6. Не применять к Production без отдельного решения Platform Owner.

## Definition of Done (критерии завершения)

- ADR-024 принят;
- миграция существует в GitHub;
- таблицы и связи соответствуют ADR;
- RLS проверена положительными и отрицательными тестами;
- создание компании атомарно создаёт владельца-члена;

- Diff Check не содержит посторонних изменений;
- Migration Check подтверждает GitHub ↔ TEST;
- документация обновлена;
- Production не изменён.
